# ADR-0004: Roles of the coding agents

## Status

Accepted, 2026-11-01. Amended 2026-11-01: Copilot may commit accepted suggestions. Amended 2026-11-03: the lead reads and writes the organisation's repositories through the Claude GitHub App. Corrected 2026-11-03: GitHub attributes the lead's actions to the maintainer's account, so its limits are procedural.

## Context

Code is written with AI assistance and reviewed by behaviour ([GOVERNANCE.md](../../GOVERNANCE.md)). Three agents are available: a local model on the maintainer's own hardware, Claude (cloud) and GitHub Copilot. They differ in cost, privacy and capability: the local model is free to run and private but has a smaller context window and is weaker at multi-step work; Claude is stronger at design, review and security-sensitive code; Copilot is built into GitHub and the editor. Without fixed roles, work drifts to whichever tool is open, and nobody owns the backlog or the review.

## Decision

| Role | Agent | Owns |
| :-- | :-- | :-- |
| **Implementer** | Local model, through Claude Code | Writes the code and tests for one issue at a time, from a brief; opens the pull request |
| **Lead** | Claude | Turns issues into briefs, keeps the backlog and labels current, reviews every pull request, fixes what the implementer got wrong, keeps `docs/` in step with the code, runs the Milestone 0 spikes |
| **Assistant** | GitHub Copilot | Pull request summaries, commit messages for hand-made commits, a second automated review with suggested changes on every pull request; commits only when the maintainer accepts a suggestion or asks it to fix something |
| **Maintainer** | @atterdag | Decides; merges; owns the architecture, threat model and security properties |

The workflow, the brief format and the status labels are in [AGENTS.md](../../AGENTS.md#roles-and-workflow). Every change still passes the same required checks and is merged by the maintainer.

Spikes stay with the lead: they need upstream research the local model cannot do offline.

### Amendment 2026-11-03: the lead works in GitHub directly

The lead reads and writes the LinuxHello organisation's repositories through the Claude GitHub App installed on the organisation, not through scripts run on the maintainer's machine.

- **May:** read code, issues, pull requests, reviews, CI logs and attestations; create branches; push commits to its own branches and to pull request branches it reviews; open pull requests; comment on and label issues and pull requests.
- **May not:** push to `main`, merge, approve its own pull requests, change branch protection, rulesets, secrets or repository settings, create tags or releases, or weaken a CI gate.
- **DCO:** the lead's commits carry no `Signed-off-by:`, because an agent cannot certify the DCO. The maintainer certifies them before merge with `dco-signoff.sh <pr>`, as for Copilot coding-agent commits.
- **Credentials:** the session injects the App's credential; the lead never sees, prints or stores it, so invariant 9 still holds: it never asks for or handles a token.
- **Attribution:** the App acts on behalf of the maintainer. GitHub records the pull requests the lead opens, its comments and its edits as made by the maintainer's account (observed on #46 to #48: author `atterdag`). Only the commits carry the lead's own author identity. Rulesets and checks therefore cannot tell the lead from the maintainer, and the **May not** list above holds because the lead keeps it, not because GitHub enforces it. The lead's posts end with a "Generated by Claude Code" footer; that is a convention, not a control.
- **Certification that the lead cannot forge:** the maintainer's GPG signature. `dco-signoff.sh` re-signs the branch with his key, which the lead never has. A sign-off line in a pull request body or a comment is not enough on its own, because the lead could write either under his account. Certifying at merge from GitHub Mobile waits until the lead acts under an identity of its own.

## Consequences

**Easier:** most implementation runs locally at no cost and without sending code anywhere; briefs make each task small and checkable; review has one owner; the backlog and docs stay current because one agent is responsible for them.

**Easier (amendment 2026-11-03):** the lead reads CI logs and review comments directly and pushes fixes without a patch-and-script round trip through the maintainer.

**Harder (amendment 2026-11-03):** the lead's commits need the maintainer's DCO certification before merge; a cloud agent holding write access to the organisation is a new trust boundary. Because GitHub attributes its actions to the maintainer's account, branch protection and rulesets do not separate the two. Required checks still apply to the lead, but nothing technical stops it from merging a green pull request or writing a sign-off line in his name. The App's permissions, which the maintainer keeps to contents, pull requests, issues, checks and actions, bound what it can touch: without administration it cannot change settings or rulesets. They do not change who it appears to be. Giving the lead an identity of its own would turn the **May not** list into enforceable rules; until then, the maintainer's GPG-signed certification is the one control the lead cannot satisfy.

**Harder:** Copilot commits made by its coding agent carry no DCO sign-off, so the maintainer certifies them before merge (AGENTS.md, Copilot suggestions and the DCO); the lead must write briefs small enough for the implementer's context window, which adds a step before every issue; review load on the lead grows with the implementer's error rate; security-sensitive code written by a weaker model needs closer review; three agents mean three sets of instructions to keep in line with `AGENTS.md`.
